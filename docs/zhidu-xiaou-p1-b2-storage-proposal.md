# P1-B2 最小存储设计草案（待确认，未实施）

日期：2026-10-20。仅设计，不创建表、不执行迁移、不增加保存 API。

## 1. 目标与选型

正式目标是账号级保存、重新查看、删除、基础反馈与继续追问。云端派生结果为权威，本地仅为可失效缓存；不得把未完成云端保存显示为“已可靠保存”。

| 方案 | 可复用部分 | 不适合直接承载的部分 |
| --- | --- | --- |
| `user_entries` | 现有 trace 身份、所有权、同步版本 | 回望不是一次原始划线/解读；塞进去会污染阅读统计、Obsidian及同步协议 |
| `user_insights` | 现有私人回望/发现展示经验 | 每用户一份规则缓存，不是单书、多结果、可删除的收藏存储 |
| `xiaou_conversations/messages` | 账号隔离、私有历史、消息角色与状态 | 单靠文本消息缺少结构化结果、证据依赖及级联失效 |
| 只存 SQLite/偏好缓存 | 离线展示经验、会话与环境命名空间 | 不满足账号换设备/重装后可靠查看，不能作为正式权威 |
| 最小独立派生结果结构 | 不修改原始历史，明确保存/依赖/失效 | 需新迁移、权限检查和删除联动，必须先审批 |

建议最后一种，并复用现有私有对话保存回望追问，不另建第二套阅读/聊天历史。

## 2. 最小 PostgreSQL 结构建议

### reading_recaps

- `id UUID`、`user_id`（FK users，账号删除级联）。
- `book_id`，`schema_version`、`prompt_version`、模型标识。
- `source_fingerprint`、`coverage_json`、校验后的 `result_json`。
- `status`：valid / stale / invalidated；`is_saved`、创建/修改时间。
- `client_request_id`：用户范围内保存幂等身份；同 ID 不同 payload 应冲突。
- 可选 `conversation_id` 指向现有私有对话，绑定相同 user。
- 索引 `(user_id, book_id, updated_at)`；唯一 `(user_id, client_request_id)`。

只保存派生结果及显示必要的短引文，不保存完整书籍、整个生成输入、整份原始历史快照。结果本身可能包含私人内容，同样受删除与访问控制约束。

### reading_recap_sources

- `recap_id`、`user_id`、`book_id`、来源实体类型、稳定 client ID/远端 ID。
- 生成时版本/内容指纹，必要定位描述、证据 ID。
- 复合唯一约束防止同一依赖重复；索引按用户及来源实体反查受影响回望。
- 不复制原文正文。外键/约束应防止依赖跨用户回望；不能只靠前端过滤。
- 同时记录直接与间接依赖，例如一条追问所属 trace，避免删父记录后遗留派生答案。

### reading_recap_feedback

- `id`、`user_id`、`recap_id`、可选条目 ID。
- 枚举 inaccurate / low_value / wrong_relation，以及有长度限制的可选说明。
- 创建时间、客户端请求 ID；用户级幂等，删除回望或账号后级联删除。
- 默认不发送模型供应商、不自动用于训练、不隐式上传额外原文。

追问优先复用 `xiaou_conversations/messages`，新增受控的 recap kind/关联校验，而不是将回望追问插入某一条原始 trace 的 follow-ups。必须审查现有 kind 校验和对话删除路径，不能只添加字符串便宣称兼容完成。

这些是候选结构，不是已经决定的迁移编号或已创建的表。

## 3. 权限与保存流程

1. 已认证账号主动发起单书回望，并同意实际发送的资料范围。
2. 服务端解析依赖，核对每条已同步 trace/追问的 user/book、删除状态和版本。
3. 对本地补充片段明确标记“用户提供的阅读材料”，不能宣称服务器验证了完整图书。
4. 仅保存完成且通过结构/引用校验的结果；在保存事务内再次检查来源版本，防止生成期间删除或修改。
5. 原子写入结果与依赖；并发相同请求不会创建重复保存结果。
6. 读取时按认证 user 查询，验证依赖与状态，再返回内容；其他账号使用 ID 访问应无内容泄露。

建议先不让含“尚未同步、服务器无法确认身份”的来源获得正式云端保存成功状态。生成可继续支持本地痕迹；结果可保留本机草稿，但必须明确“尚未保存到账号”，不自动触发上传。待正常同步完成后重新检查再保存。

**这一离线草稿/云端保存区别需要产品确认。** 若要求未同步来源也立即跨设备保存，需额外设计暂存、所有权、删除通知与清理协议；不能暗中复制第二套阅读历史解决。

## 4. 删除、版本和竞态

| 事件 | 服务端 | 本地 |
| --- | --- | --- |
| 用户删除回望 | 删除结果、依赖、反馈和相应回望追问；不动原始记录 | 清除此回望缓存，返回时旧请求不得复活 |
| 来源编辑/新增追问 | 源更新事务中标记受影响结果 stale；查询也核对依赖 | 不再作为当前有效结果展示，明确需重新生成 |
| 来源删除/永久删书 | 同事务撤销派生可读性并清除含该内容的结果正文/追问；不能仅留 stale 标志继续读旧 JSON | 删除缓存与内存中的相关派生正文，不通过缓存回退展示 |
| 本地原书文件缺失 | 不据此删除合法 trace 或云端回望 | 降级为查看依据，禁用不可靠精确跳转 |
| 账号删除/退出/切换 | 删除账号按 FK 清理；普通退出不删除云端保存 | 账号切换隔离、取消请求；不把旧响应写入新会话 |

删除后的最小失效标识与保留期需确定，以便旧设备收到撤回信号；不得为调试保留已删正文。后台清理不是访问安全边界，读请求必须先拒绝失效内容。

原始表不要求全量改软删除；优先复用现有删除标记/同步 ledger，在已有写事务中加入最小的派生失效操作。其修改位置和锁顺序需实现前列清，避免破坏 Reliable Upload。

## 5. 本地缓存与离线策略

- 缓存键至少包含 API origin、userId、recapId、结果版本、来源指纹。
- 原始 SQLite user_id 并非环境命名空间，测试/正式容器仍须隔离。
- 内存及持久缓存均受 sessionEpoch 校验；A→B→A 不恢复旧请求。
- 本地编辑/删除立即失效，不等待服务器通知。
- 无法联网时无法知道另一设备刚删除的内容。要严格满足“已删私人内容不得再次展示”，建议重新打开缓存结果前取得服务端有效性证明；离线只展示不含正文的占位信息。
- 如果产品要求完整离线回看，必须明确选择可接受的撤回延迟，不能同时承诺即时跨设备删除和无限离线可读。
- 缓存失效检查不能只靠 TTL 或父 trace 的更新时间，必须覆盖追问变化。

## 6. API 与迁移草案

候选 API：创建/保存、列表、详情、删除、反馈，以及绑定 recap 的追问接口。具体路径与现有认证、响应格式一起审查后确定。列表不返回失效正文；用户身份不接受请求体自报。

迁移步骤（尚未获执行授权）：

1. 核对当时最新 migration 编号和真实 schema；保留已有 008/009 等历史。
2. additive migration 创建派生表、索引、外键/复合约束；不改写原始阅读数据。
3. 在空库和现有 schema 的合成副本上验证升级、重复执行策略及失败事务回滚。
4. 功能默认关闭；先部署兼容代码，再单独批准迁移和开放测试。
5. 正式执行前验证备份/恢复能力，生产迁移再次单独确认。

回滚：

- 功能关闭、回到不读取新表的兼容版本；保留已保存数据为默认方案。
- 不把 DROP TABLE 当作常规回滚。需要撤销结构时先导出派生数据并验证恢复，再由产品/运维明确批准。
- 新生成或缓存格式使用独立版本；旧客户端忽略新表/API，不更改原阅读与 Obsidian 协议。

## 7. B2 验收与待确认

必须覆盖保存重试/并发幂等、保存期间删除、删除后的迟到响应、同账号换设备、重新登录、A/B 隔离、追问更新失效、账号删除、缓存撤回、错误归属引用、旧客户端兼容和迁移失败恢复。

待确认：

1. 是否采用账号级派生结果存储与现有私有对话结合。
2. 未同步来源是否先保留本机草稿，待正常同步后再确认云端保存。
3. 是否接受离线重新打开时仅显示占位，以优先保证删除隐私边界。
4. 回望删除是否同时删除其专属追问（建议是）；反馈默认私有、是否以及何时上传反馈说明。

确认上述契约后再提交具体 DDL/API 与迁移测试方案，未确认前不实施 B2。
