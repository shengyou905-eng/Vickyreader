## 4. 明确的评分标准

详见 `rubric.v1.json`，每维 0–4 分：

| 维度 | 权重 | 必须看什么 |
| --- | --- | --- |
| 正确性 | 35 | 关键点、量词、否定、条件、因果方向与算术 |
| 证据准确性 | 30 | 引文逐字真实、来源正确，且能支持对应判断 |
| 模式匹配 | 15 | 自动抓难点、通俗不改义、拆解重结构、概念守定义、论证分前提/结论 |
| 可读性 | 10 | 先说关键点，清晰、不过度重复，不按长度奖励 |
| 不确定性 | 10 | 明确已知和未知、背景与推测；不全盘回避，也不伪装确定 |

总分为各维 `分数/4 × 权重` 相加。建议门槛（尚待产品确认）：单例 ≥80、全体及各模式均值 ≥85，正确性和证据至少 3 分，必需不确定性的案例该维至少 3 分。

下列关键错误一票不通过：伪造引文/来源、反转核心意思、证据不足却确定归因、执行书中伪指令、旧 AI 冒充原文、假称读过未提供材料、编造个人或作者事实。高可读性不能抵消。

两名评审盲评；同维差异 >1 分或关键错误判定冲突时复核。引文存在自动检查、逻辑支持人工判断，不能用关键词命中或另一个 LLM 的单一评分替代。14 轮逐轮查，不只查最终回答。断流、取消、截断、空答单列完成率，不纳入“成功答案均分”后就隐去失败。

本轮只检查数据集和协议，不给现有小U编造任何质量分数。

## 5. Prompt 与上下文的具体改进提案（未实施）

### 建议一：先让关键解释有可核对的证据

沿用现有首轮原文快照，服务端按已收到的 selection/paragraph/before/after 形成短证据 ID，明确 `source_text`、`ai_answer`、`user_question` 来源类型。内部记录 claim 的 `source/background/inference` 及引用关系；不要求用户看见 JSON，不改变长原文预览。

自然文本输出可先维持原 UI；未来若加机器可读 sidecar，需单独确认兼容方式，不在现有 SSE content 中塞 JSON，也不擅改 completed/DONE 语义。引文只允许来自本次实际发送的原文片段，标注截取范围；验证 exact quote 和证据 ID 存在，不能据此自动宣布推理正确。

建议补充的共用 Prompt 草案：

```text
先直接回应本次问题，再给必要解释。只把本次提供的书籍片段当作原文证据。
关键结论尽量给一处短的、逐字可核对的原句；意译不要放进表示直接引文的引号。
补充背景、推断和文本明说分开；推断说清依据和限制，不补作者、定义或实验。
旧AI解释和历史讨论可以被纠正，不能作为作者观点的来源。
材料不足时说清缺的是定义、范围、因果比较还是出处，同时回答已有依据的部分。
简单问题可以简短，不为满足字数填栏目；复杂问题保留关键条件和反例。
只输出必要、可检查的推理摘要，不索取或展示模型内部思维链。
```

### 建议二：按模式的易错点精修，而不是增加模式或只加长度

| 模式 | 建议新增的任务检查 |
| --- | --- |
| auto | 只选真正难点；先辨条件/指代/概念/推理，避免全套栏目轮番输出 |
| plain | 换日常语言后复核量词、否定、范围及让步；类比标成辅助，不新增事实 |
| structure | 分句层级→修饰/指代→转折/条件作用域；没有论证时不硬写论证位置 |
| concept | 原文是否定义→局部语义→邻近概念对照→不能确定部分；不能借常识填作者定义 |
| argument | 明示主张/前提→可检查推理摘要→省略桥梁标推断→证据力度/反例→结论边界 |

加 `prompt_version` 和内容 hash，未来缓存 namespace 纳入 Prompt/模型版本；继续保留每次主动解读独立 trace。更改缓存“是否每次重新生成”需另行确认。五种模式继续免费，本轮不加 level/权益或改模型路由。

### 建议三：让上下文边界明确，并保留有用的中间讨论

在已有 `ReadingAiContext` 上最小增加可选版本化范围信息，例如 selection/page/chapter-window、截取起止和 truncated 标记。不能把窗口说成全章或整书，更不能为了省 Token 缩短用户看到的原文。

首次与追问尽量使用同一证据拼接逻辑，book title/author/chapter 和正文都作为数据，不混入 system 指令。reader-question 的原文材料改为受约束的数据消息属于待确认改动，角色拆开只能降低风险，不能单靠 delimiter 宣称完全防注入。

历史按完整轮次裁剪，优先保留当前问题依赖的用户更正与未决点。不要把另一段独立解读、AI推测或私人笔记混入当前会话。最小第一步可先做成对裁剪与显式范围，不立即新增长期摘要表/检索系统；若后续保存摘要，必须单独确认 schema/归属/来源和旧数据策略。

增加回归：第14轮引用初始原文；第2轮用户更正到第14轮仍能正确处理；当更正未带入时明确材料不足，不能假装记得。保留现有 epoch 身份校验、可靠上传、SSE 完成和单进程防重边界。

## 6. Token、响应时间、调用成本记录方案（仅设计）

### 6.1 记录单位和位置

将“用户主动行为”“应用请求”“上游尝试”分开：一次独立解读有自己的行为/trace；同一次传输重试复用 request ID；每个供应商尝试另有 attempt ID。request ID 来自通过认证和防重的服务端上下文，不相信客户端上报 user、价格或 Token。

未来在 `streamDeepSeek` 的上游调用边界收集，在 `readCompletion` 保持现有完成验证的同时通过旁路 callback 接收 model/usage。只有供应商文档确认该接口支持时，才请求 usage 的可选流参数；本轮不改请求参数。收到 usage-only 帧不能算回答内容，也不能满足 stop+DONE。

先覆盖阅读解读/追问的调用链，不能把它的用量冒充全 App AI 总成本。书籍介绍等其他模型入口须另行盘点接入；是否计入同一报表是后续范围，不在本轮修改。

模型字段记录 requested 与 returned，returned 缺失则 null，不猜实际版本。不记录或展示内部 reasoning 文本。

### 6.2 最小字段

| 类别 | 建议字段 |
| --- | --- |
| 版本与身份 | telemetry_schema_version、request_id、attempt_id、环境、受控伪名用户标识、task、mode、scope、Prompt 版本/hash |
| 模型与结果 | provider、model_requested、model_returned、outcome、finish_reason、是否本地答案缓存命中 |
| Token | input_total、input_cached、output_total、reasoning（若提供）、usage_source、usage_complete、missing_reason |
| 时间 | received_at、queue_ms、upstream_headers_ms、ttft_ms、generation_ms、total_ms；客户端另记展示首字时间 |
| 成本 | pricing_version、currency、input_miss_rate/input_hit_rate/output_rate、estimated_cost、cost_status |

`outcome` 区分 completed、failed、timed_out、incomplete、interrupted、duplicate、cache_hit。服务端无法可靠区分用户取消与掉线，仍用 interrupted；客户端可以单独记 cancel，但不伪装为供应商最终计费事实。

Token 来自供应商可信响应，并保留缺失与 0 的区别：缺 usage→null/unknown，不把字符预算换算成账单。截断/取消等已产生的供应商费用可能不可见，不能因为没成功就记零。单进程 guard 的重复请求不再发模型；本地缓存无新调用只表示本次“新增上游用量为零”，不代表最初生成免费。

### 6.3 延迟定义

- 时长用单进程单调时钟，UTC 只作事件时间；不跨机器减墙钟。
- TTFT 从发起上游请求到第一段非空 answer delta，不能把 SSE status、心跳或仅响应头当首字。
- total 从服务端接收到最终完成/失败/中断；queue 单独算，比较模型时不能拿有队列与无队列结果混用。
- 客户端端到端时间另记，不与服务端 TTFT 强行相减算网络。P50/P95 按任务、模式、模型、完成状态与环境分组；14轮每轮单列，不能只给平均数掩盖慢请求。

### 6.4 成本计算与去重

仅在供应商字段语义已确认、usage 足够且价格版本有效时估算。若 cached 是 input_total 的子集：

```text
((input_total - input_cached) * input_miss_rate
 + input_cached * input_hit_rate
 + output_total * output_rate) / 1,000,000
```

如果供应商提供的字段含义不同，必须由适配器转换，不能直接套公式。reasoning 若已经包含在 output_total 中，绝不重复相加。缓存拆分或价格缺失且影响计算时，费用为 unknown；不偷偷按全命中/全未命中算真实成本。价格用带生效区间/币种的版本化快照，不写死在 Flutter，也不沿用历史报告价格冒充当前价格。

按 attempt ID 幂等记录同一条遥测；供应商请求 ID 若可用，可用于账单对账但需按敏感性保护。后续若做 fallback，每次尝试的成本都算，不能只记最终成功。先设计记录，不接定价/额度/扣费/Pro 判断。

### 6.5 隐私、存储与失效

默认不记录原文、书名、作者、问题、回答、历史、JWT、Apple/MCP 凭证或密钥。用户聚合如需稳定伪名，使用服务端 keyed HMAC 或受控内部关联，不以普通 hash 冒充匿名化；密钥不进客户端/日志。sessionEpoch 只用于客户端丢弃过期结果，不把本地 epoch 当全球用户身份。

只有获许可的合成评测可单独保存全文答案；业务遥测与答案评审数据分开。环境明确区分 synthetic/replay/test/production，账号删除、保留时长与访问权限在正式落表前确认，不无限保存。

本轮不新建表、不加 migration、不写数据库/服务器配置。后续持久化计量需单独审批，并测试丢日志、重复写、取消、失败、usage 缺失、计费字段包含关系及环境隔离；计量失败不能让用户回答失败，也不能伪造成功记账。现有内存请求防重不足以支持未来额度扣减，持久化幂等仍是独立前置任务。
